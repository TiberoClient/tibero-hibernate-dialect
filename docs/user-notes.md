# 사용자 안내 — 6.6.1

6.6.0 에서 6.6.1 로 올릴 때 **알아야 할 것**과 **대응 방법**을 모았습니다.
짧은 변경 고지는 [CHANGELOG.md](CHANGELOG.md) 에 있고, 이 문서는 절차와 SQL 을 담습니다.

## 이 문서에 있는 것

| # | 항목 | 성격 |
|---|---|---|
| 1 | JSON 컬럼을 쓰려면 Jackson 또는 JSON-B 가 필요합니다 | 준비 사항 |
| 2 | 저장 프로시저 파라미터는 기본이 위치 바인딩입니다 | 준비 사항 |
| 3 | **동작 변경** — month / quarter / year 연산이 시각을 보존합니다 | ⚠️ 결과가 달라짐 |
| 4 | **동작 변경** — IDENTITY 컬럼이 `generated by default as identity` 로 생성됩니다 | ⚠️ DDL 이 달라짐 |
| 5 | **동작 변경** — `str()` 의 결과 형식이 고정됩니다 | ⚠️ 결과가 달라짐 |
| 6 | 예약어 자동 인용은 옵트인입니다 | 선택 기능 |
| 7 | **동작 변경** — 네이티브 쿼리의 `NUMBER(p,0)` 결과 타입이 달라집니다 | ⚠️ 타입이 달라짐 |

> **검증 환경** — Tibero **7.2.6** (FS02_PS06) / `hibernate-core 6.6.56.Final` / `tibero7-jdbc-11`
> 아래 "실측" 표시가 붙은 결과는 실제로 실행해 얻은 것입니다.

> ⚠️ **버전 하한은 자동으로 검사되지 않습니다.** dialect 는 Tibero 6 이하에 붙으면
> `HHH000511` 경고를 남기지만, **7.2.6 미만의 7.x 는 걸러내지 못합니다.** tbjdbc 가
> 마이너 버전을 유실해(`getDatabaseMinorVersion()` 이 항상 `0`) 표준 JDBC 메타데이터로는
> 7.0 과 7.2.6 을 구분할 수 없기 때문입니다. 서버 버전은 배포 전에 직접 확인하세요.

# 1. JSON 컬럼 사용 시 주의 — JSON 직렬화 라이브러리가 별도로 필요합니다

## 요약

Tibero dialect 는 `json` 컬럼 DDL 생성과 값 바인딩을 지원합니다.
다만 엔티티 필드에 **`@JdbcTypeCode(SqlTypes.JSON)`** 을 쓰려면
**Jackson 또는 JSON-B 구현체를 프로젝트에 직접 추가**해야 합니다.

Hibernate 가 Java 객체 ↔ JSON 문자열 변환에 쓰는 `FormatMapper` 를
**클래스패스에서 자동 탐지**하는데, `hibernate-core` 자체는 이 라이브러리를 포함하지 않기 때문입니다.
이는 Tibero dialect 의 제약이 아니라 **Hibernate 공통 동작**이며 Oracle 등 다른 dialect 도 동일합니다.

## 증상

라이브러리가 없으면 **테이블 생성과 애플리케이션 기동은 정상적으로 끝나고,
JSON 값을 처음 읽거나 쓰는 시점에** 아래 예외가 발생합니다.

```text
org.hibernate.HibernateException:
Could not find a FormatMapper for the JSON format, which is required for mapping JSON types.
JSON FormatMapper configuration is automatic, but requires that you have either Jackson
or a JSONB implementation like Yasson on the class path.
```

기동 시점에 드러나지 않으므로, JSON 을 쓰는 기능이 실제로 호출될 때까지 발견되지 않을 수 있습니다.

| 단계 | 라이브러리 없음 | 있음 |
|------|-----------------|------|
| `create table` | 정상 | 정상 |
| 애플리케이션 기동 | 정상 | 정상 |
| **첫 JSON 값 저장/조회** | **예외** | 정상 |

## 해결 1 — Jackson 추가 (권장)

**Spring Boot** 를 쓴다면 버전을 적지 마세요. Spring Boot BOM 이 관리합니다.

```groovy
implementation 'com.fasterxml.jackson.core:jackson-databind'
```

```xml
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
</dependency>
```

**Spring Boot 가 아니면** 버전을 명시합니다.

```groovy
implementation 'com.fasterxml.jackson.core:jackson-databind:2.17.2'
```

> **`spring-boot-starter-web` 을 쓰고 있다면 이미 들어 있습니다.**
> 이 스타터가 `spring-boot-starter-json` 을 통해 Jackson 을 가져오므로 추가 설정이 필요 없습니다.
> 반대로 **`spring-boot-starter-data-jpa` 만 쓰는 배치·서비스 애플리케이션**에는 Jackson 이 없을 수 있으니
> JSON 매핑을 쓴다면 위 dependency 를 직접 넣어야 합니다.

## 해결 2 — JSON-B 구현체 추가

Jackson 대신 JSON-B(Yasson) 를 써도 됩니다.

```groovy
implementation 'jakarta.json.bind:jakarta.json.bind-api:3.0.0'
implementation 'org.eclipse:yasson:3.0.3'
```

> 이 프로젝트에서 실측 검증한 것은 **Jackson 경로**입니다.
> JSON-B 는 Hibernate 가 공식적으로 지원한다고 명시한 대안이며 별도 검증은 하지 않았습니다.

## 해결 3 — 라이브러리 없이 네이티브 `json` 컬럼만 쓰기

**직렬화는 애플리케이션이 직접 하고, 컬럼 타입만 `json` 이면 되는 경우**에는
`@JdbcTypeCode` 를 쓰지 않고 컬럼 정의만 지정하면 됩니다. 이 경로는 **추가 dependency 가 필요 없습니다.**

```java
@Entity
public class Doc {
    @Id
    Long id;

    @Column(columnDefinition = "json")
    String payload;          // 애플리케이션이 JSON 문자열을 직접 다룸
}
```

실측 결과 — Jackson 없이 정상 동작하며, 생성된 컬럼 타입도 네이티브 `JSON` 입니다.

```text
저장한 값   {"a":1}
읽은 값     {"a":1}
컬럼 타입   JSON        (user_tab_columns.data_type)
```

## 어떤 경우에 필요한지 정리

`FormatMapper` 를 불러오는 것은 값의 Java 타입이 아니라 **`@JdbcTypeCode(SqlTypes.JSON)` 선언 자체**입니다.
필드가 `String` 이어서 직렬화할 것이 없어도 매퍼를 찾습니다.

| 매핑 방식 | 추가 라이브러리 | 생성 컬럼 | 용도 |
|-----------|-----------------|-----------|------|
| `@JdbcTypeCode(JSON)` + POJO / `Map` | **필요** | `json` | 객체 ↔ JSON 자동 변환 |
| `@JdbcTypeCode(JSON)` + `String` | **필요** | `json` | (직렬화가 없어도 필요) |
| `@Column(columnDefinition = "json")` + `String` | 불필요 | `json` | 앱이 JSON 문자열을 직접 관리 |

## 매퍼를 직접 지정하려는 경우

자동 탐지 대신 구현체를 명시하려면 아래 설정을 씁니다.

```properties
hibernate.type.json_format_mapper=<FormatMapper 구현 클래스 또는 등록된 별칭>
```

Spring Boot에서는 `spring.jpa.properties.` 접두사를 붙입니다.

```properties
spring.jpa.properties.hibernate.type.json_format_mapper=...
```

## 사용 예시

Jackson 을 추가한 뒤에는 아래가 모두 동작합니다. (ps06 실측)

```java
@Entity
public class Doc {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    Long id;

    @JdbcTypeCode(SqlTypes.JSON)
    Map<String, Object> payload;

    @JdbcTypeCode(SqlTypes.JSON)
    Addr addr;                       // 임의의 POJO
}
```

```text
생성 DDL   create table DOC (id number(19,0) generated as identity,
                             addr json, payload json, primary key (id))
저장 원문   {"k":"v","n":42}
왕복 결과   payload = {k=v, n=42}   /   addr = Seoul/6236
```

# 2. 저장 프로시저 파라미터 — 기본은 **위치 바인딩**입니다

## 요약

`StoredProcedureQuery` / `ProcedureCall` 에 파라미터를 **이름으로 등록해도**,
Hibernate 는 기본 설정에서 이름을 버리고 `?` 만 나열합니다.
결과적으로 **등록한 순서대로 위치 바인딩**됩니다.

프로시저 선언 순서와 등록 순서가 다르면 **예외 없이 값만 뒤바뀝니다.**

이는 Tibero dialect 의 제약이 아니라 **Hibernate 의 의도된 기본 동작**이며
Oracle 을 포함한 모든 dialect 가 동일합니다.

## 증상

```sql
create or replace procedure P(p_a in number, p_b in number, p_out out number) is
begin p_out := p_a*100 + p_b; end;
```

```java
var call = session.createStoredProcedureCall("P");
call.registerParameter("p_b", Integer.class, ParameterMode.IN);   // 선언 순서와 다르게 등록
call.registerParameter("p_a", Integer.class, ParameterMode.IN);
call.registerParameter("p_out", Integer.class, ParameterMode.OUT);
call.setParameter("p_b", 7);
call.setParameter("p_a", 3);
call.execute();
```

| | 실제 호출문 | `p_out` |
|---|-------------|---------|
| 기본 설정 | `{call P(?,?,?)}` | **703** ← p_b 가 p_a 자리로 들어감 |
| 이름 바인딩 | `{call P(p_b => ?, p_a => ?, p_out => ?)}` | **307** (기대값) |

**예외가 발생하지 않으므로** 값이 틀린 채로 넘어갑니다.

## 해결 1 — 선언 순서대로 등록 (설정 불필요, 권장)

가장 단순하고 어떤 설정에서도 안전합니다.

```java
call.registerParameter("p_a", Integer.class, ParameterMode.IN);    // 선언 순서 그대로
call.registerParameter("p_b", Integer.class, ParameterMode.IN);
call.registerParameter("p_out", Integer.class, ParameterMode.OUT);
```

위치로 등록해도 동일합니다.

```java
call.registerParameter(1, Integer.class, ParameterMode.IN);
```

## 해결 2 — 이름 바인딩을 켜기

이름으로 넘기고 싶다면 아래 설정을 켭니다.

```properties
hibernate.query.pass_procedure_paramater_names=true
```

Spring Boot 에서는 `spring.jpa.properties.` 접두사를 붙입니다.

```properties
spring.jpa.properties.hibernate.query.pass_procedure_paramater_names=true
```

> ⚠️ **키 이름의 `paramater` 는 오타가 아닙니다.**
> Hibernate 가 정의한 설정 키 자체에 오타가 있어 **그대로 써야** 동작합니다.
> `parameter` 로 고쳐 쓰면 설정이 무시되고 조용히 위치 바인딩으로 돌아갑니다.

이 설정을 켜면 Tibero dialect 6.6.1 이상에서 아래 형태로 나갑니다.

```sql
{call P(p_a => ?, p_b => ?, p_out => ?)}
```

실측 결과 Tibero 는 이 Oracle 호환 `이름 => 값` 표기를 정상 해석합니다.
등록 순서를 뒤집어도 `p_out = 307` 로 올바르게 나옵니다.

## 버전별 동작

| dialect 버전 | 설정 OFF (기본) | 설정 ON |
|--------------|-----------------|---------|
| 6.6.0 이하 | 위치 바인딩 | **위치 바인딩** — 설정을 켜도 이름이 안 나감 |
| 6.6.1 이상 | 위치 바인딩 (표준과 동일) | **이름 바인딩** |

6.6.0 이하에서는 설정을 켜도 효과가 없었습니다.
`TiberoCallableStatementSupport` 가 6.6.1 에서 추가되면서 켤 수 있게 되었습니다.

## 정리

| 상황 | 권장 |
|------|------|
| 파라미터가 적고 순서를 맞출 수 있음 | **해결 1** — 선언 순서대로 등록 |
| 파라미터가 많거나 순서를 보장하기 어려움 | **해결 2** — 설정을 켜고 이름 바인딩 |
| 기본값(OFF) 으로 두고 이름 등록만 함 | ⚠️ 순서가 어긋나면 **조용히 값이 틀림** |

# 3. 동작 변경 — month / quarter / year 연산이 **시각을 보존**합니다

> **성격이 다른 항목입니다.** 1·2항은 "이렇게 쓰세요"이고, 이 항목은
> **"이전 버전 및 Oracle dialect 와 결과가 달라졌습니다"** 라는 변경 고지입니다.
> 릴리즈 노트에 반드시 들어가야 합니다.

## 요약

`6.6.1` 부터 HQL 의 `+ n month` / `+ n quarter` / `+ n year` 연산이
**TIMESTAMP 의 시·분·초를 그대로 유지**합니다.

이전에는 시각이 `00:00:00` 으로 깎였습니다. **Oracle dialect 는 지금도 깎습니다.**
따라서 같은 HQL 을 Oracle 과 Tibero 에 돌리면 **결과가 다릅니다.**

## 무엇이 달라졌나

기준 값 `ts = 2024-01-31 10:20:30`

| HQL | 6.6.0 이하 · **Oracle dialect** | **6.6.1 이상** |
|-----|-------------------------------|----------------|
| `ts + 1 month` | `2024-02-29 00:00:00` | **`2024-02-29 10:20:30`** |
| `ts + 1 quarter` | 시각 유실 | **`2024-04-30 10:20:30`** |
| `ts + 1 year` | 시각 유실 | **`2025-01-31 10:20:30`** |
| `ts - 1 month` | 시각 유실 | **`2023-12-31 10:20:30`** |

**바뀌지 않은 것**

- **월말 클램프는 그대로입니다** — `1/31 + 1개월` 은 여전히 `2/29`(윤년) 로 잘립니다
- **DATE 타입은 영향 없습니다** — 애초에 시각이 없으므로 결과가 동일합니다
- **일 이하 단위(day / hour / minute / week) 는 영향 없습니다** — 원래도 시각을 보존했습니다

## 왜 바꿨나

시각을 버리는 것은 Hibernate 공통 동작이 아니라 **Oracle dialect 한 곳만의 특성**입니다.
PostgreSQL · MySQL · SQL Server · H2 · DB2 · HSQL 은 모두 시각을 보존하고, 그 동작을 설명하는
주석이나 문서도 없어 약속된 계약으로 보기 어려웠습니다. 그래서 다수 쪽에 맞췄습니다.

## 영향 범위

아래를 쓰는 코드가 영향을 받습니다.

```java
// HQL / JPQL
"select e from Order e where e.createdAt + 1 month > :now"
"select timestampadd(month, 3, e.ts) from Order e"

// Criteria
cb.function("timestampadd", ...)  // month / quarter / year 단위
```

**대부분의 경우 값이 더 정확해지는 방향**이므로 별도 조치가 필요 없습니다.
다만 아래 두 경우는 확인이 필요합니다.

| 상황 | 확인할 것 |
|------|-----------|
| 기존 결과가 `00:00:00` 인 것에 의존하는 코드 | 예: `where e.ts + 1 month = :midnight` 같은 비교. `trunc()` 를 명시적으로 쓰도록 바꿔야 합니다 |
| Oracle ↔ Tibero **결과 대조**로 이식성을 검증하는 경우 | month 계열 연산에서 차이가 납니다. 위 표를 근거로 사용하세요 |

## 이전 동작이 필요하다면

`trunc()` 를 명시적으로 쓰면 됩니다. 의도가 코드에 드러나므로 오히려 권장되는 형태입니다.

```java
// 시각을 버리고 날짜만 쓰고 싶을 때
"select trunc(e.ts + 1 month) from Order e"
```

# 4. 동작 변경 — IDENTITY 컬럼이 `generated by default as identity` 로 생성됩니다

> **3항과 같은 변경 고지입니다.** 릴리즈 노트에 반드시 들어가야 합니다.
> 새로 만드는 스키마에만 적용되며, **이미 6.6.0 으로 만든 테이블은 그대로 남습니다.**
> 그대로 두어도 동작에는 문제가 없지만, 전환하려면 ALTER 로는 안 되고
> 테이블을 다시 만들어야 합니다 — 아래 "이미 6.6.0 으로 만든 테이블이 있다면" 참고.

## 요약

`@GeneratedValue(strategy = IDENTITY)` 로 만들어지는 컬럼의 DDL 이 바뀝니다.

| dialect 버전 | 생성 DDL |
|--------------|----------|
| 6.6.0 이하 | `id number(19,0) generated as identity` — **`always` 의미** |
| **6.6.1 이상** | `id number(19,0) generated by default as identity` |

효과는 하나입니다 — **ID 를 직접 지정한 INSERT 가 허용됩니다.**

```sql
-- 6.6.0
insert into ORDERS (id, name) values (999, 'x');   -- JDBC-8162 거부
-- 6.6.1
insert into ORDERS (id, name) values (999, 'x');   -- 성공
```

애플리케이션 코드에서 `persist()` 로 저장하는 통상 경로는 **아무것도 달라지지 않습니다.**
자동 채번도, `getGeneratedKeys()` 로 ID 를 회수하는 동작도 그대로입니다.

## 왜 바꿨나

`always` 는 데이터 이관·시드 스크립트처럼 **원래 ID 를 보존해야 하는 작업을 막습니다.**
애플리케이션은 정상 동작하다가 이관 시점에 실패하므로 발견이 늦습니다.

그리고 `always` 는 Hibernate 안에서 Tibero 만의 선택이었습니다. 표준
`generated … as identity` 문법을 쓰는 dialect 6종(Oracle · PostgreSQL · DB2 · H2 ·
HANA · HSQL) 이 **예외 없이 `by default`** 입니다.

## 이미 6.6.0 으로 만든 테이블이 있다면 — 그대로 쓰셔도 됩니다

기존 테이블은 **자동으로 바뀌지 않습니다.** `always` 인 채로 남습니다.
**전환하지 않아도 됩니다.** 대부분의 경우 아무것도 하지 않는 편이 낫습니다.

ALWAYS 테이블과 BY DEFAULT 테이블에 6.6.1 dialect 를 각각 붙여
엔티티 생명주기 전체를 돌려 비교했습니다. (실측)

| 경로 | ALWAYS (6.6.0 스키마) | BY DEFAULT (6.6.1 스키마) |
|------|----------------------|--------------------------|
| `persist()` — 단건 / 연속 | ✅ | ✅ |
| 채번된 ID 회수 (`getGeneratedKeys`) | ✅ | ✅ |
| `find` · `update` · `@Version` 증가 | ✅ | ✅ |
| 기존 행 `merge()` | ✅ | ✅ |
| 컬럼이 `@Id` 하나뿐인 엔티티 | ✅ | ✅ |
| `remove()` | ✅ | ✅ |
| **네이티브 SQL 로 ID 를 직접 지정한 INSERT** | ❌ `JDBC-8162` | ✅ |

**Hibernate 가 내는 SQL 이 애초에 ID 에 값을 넣지 않기 때문입니다.**
IDENTITY 컬럼을 컬럼 목록에는 넣지만 값 자리에는 `default` 키워드를 씁니다.

```sql
insert into ORDERS (name, ver, id) values (?, ?, default)
insert into BARE   (id)            values (default)          -- 컬럼이 id 뿐일 때
```

`default` 키워드는 ALWAYS 컬럼에도 허용되므로 두 스키마가 완전히 같게 동작합니다.
차이가 드러나는 곳은 **사용자가 직접 ID 를 써넣는 네이티브 SQL 한 곳뿐**입니다.

### 그러면 언제 전환하나요

아래에 해당할 때만 전환할 값어치가 있습니다.

- 데이터 이관·시드 스크립트에서 **원래 ID 를 보존해야** 할 때
- `import.sql` / `data.sql` 처럼 ID 를 명시한 초기 데이터를 넣을 때
- 테스트에서 ID 를 고정해 픽스처를 만들 때

전환 비용은 뒤에서 설명하듯 **테이블 재구성**이라 싸지 않습니다.
위에 해당하지 않으면 `always` 로 두세요.

> ⚠️ **개발 환경과 운영 환경이 갈릴 수 있습니다.**
> 개발에서 `hbm2ddl.auto=create-drop` / `create` 를 쓰면 6.6.1 로 올린 순간
> 개발 테이블만 `by default` 로 다시 만들어집니다. 운영은 `validate` / `none` 이라
> `always` 로 남습니다. 이 상태에서 ID 를 명시하는 시드 스크립트를 만들면
> **개발에서는 통과하고 운영에서 `JDBC-8162` 로 실패**합니다.
> 명시 ID 를 쓸 계획이라면 양쪽 스키마를 맞춰두세요.

현재 상태는 카탈로그에서 확인할 수 있습니다.

```sql
select table_name, column_name, generation_type
  from user_tab_identity_cols;
-- ALWAYS      → 6.6.0 시절 DDL
-- BY DEFAULT  → 6.6.1 DDL
```

`hibernate.hbm2ddl.auto=validate` 는 IDENTITY 의 `always`/`by default` 구분까지는
검사하지 않으므로, 전환하지 않아도 이 차이로 기동이 실패하지는 않습니다.

### ⚠️ ALTER 로는 전환할 수 없습니다

Oracle 이라면 `alter table … modify id generated by default as identity` 로 끝나지만,
**Tibero 에서는 이 문장이 성공을 반환하면서 아무것도 바꾸지 않습니다.** (실측)

```sql
create table ORDERS (id number generated as identity primary key, v varchar2(20));
select generation_type from user_tab_identity_cols where table_name='ORDERS';
--   → ALWAYS

alter table ORDERS modify id generated by default as identity;
--   → 성공 (오류 없음)

select generation_type from user_tab_identity_cols where table_name='ORDERS';
--   → ERROR          ← BY DEFAULT 가 아니라 잘못된 값이 됩니다

insert into ORDERS (id, v) values (500, 'x');
--   → JDBC-8162: Cannot insert into an always identity column.   ← 여전히 막힘
```

**오류가 나지 않으므로 스크립트로 일괄 실행하면 전환된 줄 알고 넘어가게 됩니다.**
반드시 `generation_type` 을 다시 조회해 확인하세요.

떼어냈다가 다시 붙이는 우회도 막혀 있습니다.

| 시도한 구문 | 결과 |
|-------------|------|
| `alter table T modify id generated by default as identity` | 성공을 반환하지만 **무효**, `generation_type` 이 `ERROR` 가 됨 |
| `alter table T modify id generated by default on null as identity` | 위와 동일 |
| `alter table T modify id drop identity` | `JDBC-7001` 구문 오류 |
| `alter table T modify (id drop identity)` | `JDBC-7001` 구문 오류 |
| `alter table T modify id number` | `JDBC-7237` Specified column 'ID' cannot be modified |
| `alter table T modify id generated always as identity` (같은 값) | 성공, `ALWAYS` 유지 — **값을 바꿀 때만 깨집니다** |

방향에 따라 결과가 다릅니다.

| 방향 | `generation_type` | 실제 동작 |
|------|-------------------|-----------|
| ALWAYS → by default | `ERROR` | **안 바뀜** — 명시 INSERT 가 여전히 막힘 |
| BY DEFAULT → always | `ERROR` | **바뀜** — 명시 INSERT 가 막히기 시작함 |

두 방향 모두 카탈로그는 깨지지만 동작은 양쪽 다 `always` 가 됩니다.
**`always` 에서 빠져나오는 것만 불가능합니다.**

### 전환하려면 테이블을 다시 만들어야 합니다

원래 ID 를 보존한 채 옮긴 뒤 시퀀스를 밀고 이름을 바꿉니다. (실측)

```sql
-- 1) by default 로 새 테이블을 만듭니다 (제약·인덱스도 함께 정의)
create table ORDERS_NEW (
    id number generated by default as identity primary key,
    v  varchar2(20)
);

-- 2) 원래 ID 를 그대로 복사합니다 — by default 이므로 명시 삽입이 됩니다
insert into ORDERS_NEW (id, v) select id, v from ORDERS;

-- 3) 시퀀스를 max(id) 다음으로 밉니다 (아래 "시퀀스를 미는 방법" 참고)

-- 4) 교체합니다
drop table ORDERS;
alter table ORDERS_NEW rename to ORDERS;
```

외래 키·트리거·뷰가 걸려 있으면 함께 다시 만들어야 하므로,
**테이블 수가 많다면 전환하지 않고 그대로 두는 편이 낫습니다.**
`always` 로 남겨두어도 애플리케이션 동작에는 문제가 없습니다.

## ⚠️ 명시 ID INSERT 를 쓸 때의 주의 — 채번 충돌

`by default` 에서 ID 를 직접 넣어도 **내부 시퀀스는 그 값을 모릅니다.**
이후 자동 채번이 이미 쓴 값을 다시 발급하면 UNIQUE 제약에 걸립니다. (실측)

```text
1. persist()          → id = 1
2. 명시 insert id = 2 → 성공   (시퀀스는 아직 1 까지만 알고 있음)
3. persist()          → JDBC-10007 UNIQUE constraint violation
                        ↑ 시퀀스가 2 를 다시 발급
```

Oracle · PostgreSQL 에도 그대로 있는 함정입니다.
ID 를 직접 넣은 뒤에는 시퀀스를 밀어주세요.

### 시퀀스를 미는 방법

> ⚠️ Oracle 에서 쓰는 `alter table T modify id generated by default as identity (start with limit value)`
> 는 **Tibero 에서 동작하지 않습니다.** `JDBC-7008: START WITH is not allowed for ALTER sequences`
> 로 거부됩니다. 괄호를 빼도, `restart` 를 붙여도 마찬가지입니다. (실측)

Tibero 는 IDENTITY 컬럼 뒤의 시퀀스를 `user_tab_identity_cols.sequence_name` 으로 노출하고,
그 시퀀스는 일반 시퀀스처럼 `alter sequence` 로 조정할 수 있습니다.
**증분을 한 번 크게 잡아 건너뛴 뒤 되돌리는** 방식을 씁니다.

```sql
-- 1) 대상 시퀀스 이름과 테이블의 최대 ID 를 확인합니다
select sequence_name from user_tab_identity_cols where table_name = 'ORDERS';
--   → ISEQ$$_6116
select max(id) from ORDERS;
--   → 12

-- 2) 시퀀스의 현재 위치를 한 번 소비해서 확인합니다
select ISEQ$$_6116.nextval from dual;
--   → 1

-- 3) (max - 현재값) 만큼 한 번에 건너뛴 뒤 증분을 1 로 되돌립니다
alter sequence ISEQ$$_6116 increment by 11;   -- 12 - 1
select ISEQ$$_6116.nextval from dual;         -- → 12  (소비)
alter sequence ISEQ$$_6116 increment by 1;
```

이후 자동 채번은 `13`, `14` … 로 이어집니다. (실측)

이관·시드처럼 **한 번에 넣고 끝나는 작업**에서는 적재가 모두 끝난 뒤 한 번만 실행하면 됩니다.
운영 중에 명시 ID 와 자동 채번을 **섞어 쓰는 설계는 권장하지 않습니다.**

> `ISEQ$$_…` 이름은 테이블을 다시 만들면 바뀌므로 **하드코딩하지 말고**
> 위 1) 의 조회로 매번 얻으세요. `$` 가 들어가지만 따옴표 없이 그대로 써도 됩니다.

# 5. 동작 변경 — `str()` 의 결과 형식이 고정됩니다

## 요약

HQL `str(x)` 는 값을 문자열로 바꾸는 함수입니다. 6.6.0 까지는 결과가 **접속 세션의 NLS
설정에 좌우**되었고, 6.6.1 부터 날짜·시각·타임스탬프가 **ISO-8601 로 고정**됩니다.

```
                              6.6.0                6.6.1
NLS_DATE_FORMAT 기본          "2024/03/05"         "2024-03-05"
NLS_DATE_FORMAT='DD/MM/YYYY'  "05/03/2024"  ←달라짐  "2024-03-05"  ←고정
```

## 왜 문제였나

세션 설정은 애플리케이션이 아니라 **접속 환경**이 정하는 경우가 많습니다. 개발 장비에서
맞던 것이 운영에서 달라지고, 그 문자열을 파싱하거나 비교하는 코드가 **예외 없이** 깨집니다.

## 무엇이 바뀌었나

| 타입 | 6.6.1 결과 | NLS 영향 |
|---|---|---|
| 날짜 | `2024-03-05` | 없음 |
| 시각 | `11:22:33` | 없음 |
| 타임스탬프 | `2024-03-05 11:22:33.000000000` | 없음 |
| 오프셋 타임스탬프 | `2024-03-05 11:22:33.000000000+09:00` | 없음 |
| 정수 | `42` | 없음 |
| **소수 · double** | `1234.5` | ⚠️ **`NLS_NUMERIC_CHARACTERS` 를 탐** |

**숫자는 여전히 세션 설정을 탑니다.** `cast(숫자 as varchar2)` 자체의 성질이라
`str` 만 고쳐서 될 일이 아니며, **Oracle 도 동일**합니다.

## 대응

이전 형식에 의존하는 코드가 있으면 형식을 직접 지정하세요. 그러면 NLS 와 무관하게 고정됩니다.

```sql
to_char(e.day,  'YYYY/MM/DD')      -- 이전 형식이 필요할 때
to_char(e.price,'FM999999D000')    -- 숫자 형식을 고정하고 싶을 때
```

# 6. 예약어 자동 인용은 옵트인입니다

## 요약

Tibero 고유 예약어 71종을 dialect 에 등록했습니다. `size`·`comment`·`level` 같은 이름을
컬럼명으로 쓸 때 자동으로 인용됩니다. 다만 **기본값이 꺼져 있어** 설정을 켜야 동작합니다.

```properties
spring.jpa.properties.hibernate.auto_quote_keyword=true
```

기본값이 `false` 인 것은 Hibernate 의 결정이고 **Oracle 도 같습니다.** 우리가 바꿀 수 있는
값이 아닙니다.

## 켤 때 주의 — 대소문자가 고정됩니다

인용된 식별자는 **적은 그대로** 만들어집니다. 소문자로 선언하면 소문자 컬럼이 생기고,
그 뒤로는 조회할 때도 항상 인용해야 합니다.

```java
@Column(name = "size")     // → "size"  (소문자 컬럼)
@Column(name = "SIZE")     // → "SIZE"  (권장)
```

```sql
select size from T;     -- JDBC-8008  소문자 컬럼을 못 찾음
select "size" from T;   -- OK
```

**예약어를 컬럼명으로 쓸 때는 대문자로 선언하는 편이 안전합니다.**

## 등록된 예약어

실측으로 확정한 71종입니다. Tibero 카탈로그의 `V$RESERVED_WORDS` 에서 `RESERVED='Y'` 인
것만 고르면 **13개를 놓칩니다** — `least`·`flashback`·`connect_by_root` 등은 플래그가
`N` 인데도 컬럼명으로 쓰면 `create table` 이 실패합니다. 그래서 1,242개 전체를 실제로
컬럼명으로 만들어 보고 가려냈습니다.

# 7. 동작 변경 — 네이티브 쿼리의 `NUMBER(p,0)` 결과 타입이 달라집니다

## 요약

네이티브 쿼리로 `NUMBER(p,0)` 컬럼을 읽을 때 돌려받는 자바 타입이 바뀝니다.

| 컬럼 타입 | 이전 | 6.6.1 |
|---|---|---|
| `NUMBER(1,0)` | `Boolean` | **`Integer`** |
| `NUMBER(3,0)` | `Byte` | **`Integer`** |
| `NUMBER(5,0)` | `Short` | **`Integer`** |
| `NUMBER(10,0)` | `Integer` | `Integer` (그대로) |
| `NUMBER(19,0)` | `Long` | `Long` (그대로) |
| `NUMBER(38,0)` · 집계 | `BigDecimal` | `BigDecimal` (그대로) |

규칙은 **`p ≤ 10` → `Integer`, `p ≤ 19` → `Long`, 그 밖 → `BigDecimal`** 입니다.

**엔티티 매핑은 영향이 없습니다.** 엔티티 필드는 이 경로가 아니라 매핑 모델을 타므로
`Boolean flag` 필드는 그대로 `Boolean` 이고, `@Column` 으로 만드는 DDL 도 그대로입니다.
바뀌는 것은 **DB 가 알려주는 컬럼 정보만 보고 타입을 정해야 하는 자리** — 네이티브 쿼리
결과, 스키마 검증, `hbm2ddl update` 입니다.

## 왜 바꿨나

**DB 쪽 범위가 자바 타입보다 넓기 때문입니다.**

```
number(1,0)   -9 ~ 9          Boolean 은 참/거짓 둘뿐
number(3,0)   -999 ~ 999      Byte  는 -128 ~ 127
number(5,0)   -99999 ~ 99999  Short 는 -32768 ~ 32767
```

컬럼에 **정상적으로 들어가는 값**인데도 읽을 때 깨졌습니다. ps06 실측입니다.

```
DB 값: b1=7, b3=200, b5=50000

이전   b1 => true                                          ← 예외 없이 7 이 true 로
       b3 => JDBC-590749:Invalid data type: corrupted data format. - 200
       b5 => JDBC-590749:Invalid data type: corrupted data format. - 50000

6.6.1  b1 => 7        b3 => 200        b5 => 50000
```

`b1` 이 가장 위험했습니다 — 오류가 나지 않고 값만 바뀌므로 알아차릴 방법이 없었습니다.

Hibernate 의 `OracleDialect` 도 같은 이유로 이 추론을 하지 않습니다. 소스에 사유가
주석으로 남아 있습니다 — *"Don't infer TINYINT or SMALLINT on Oracle, since the range of
values of a NUMBER(3,0) or NUMBER(5,0) just doesn't really match naturally."*

## 영향 범위와 대응

`ddl-auto` 로 이 dialect 가 만든 스키마만 쓰고 있다면 드러나지 않습니다. `Byte` 필드에는
127 이하만 들어가기 때문입니다. 문제가 되는 것은 **dialect 가 만들지 않은 기존 스키마를
읽을 때** 입니다 — 기존 Tibero DB 에 Spring/JPA 를 얹는 경우가 여기 해당합니다.

**대응이 필요한 코드**는 네이티브 쿼리 결과를 이전 타입으로 캐스팅하는 곳입니다.

```java
// 이전 타입에 맞춰 둔 코드 — 6.6.1 에서 ClassCastException
Boolean flag = (Boolean) em.createNativeQuery("select flag from T").getSingleResult();

// 대응 1 — Integer 로 받기
Integer flag = (Integer) em.createNativeQuery("select flag from T").getSingleResult();
boolean on = flag != null && flag != 0;

// 대응 2 — 결과 타입을 명시하기 (권장)
Boolean on = em.createNativeQuery("select flag from T", Boolean.class).getSingleResult();
```

**대응 2 를 권합니다.** 결과 타입을 명시하면 dialect 의 추론과 무관하게 원하는 타입으로
변환되므로, 앞으로 이 규칙이 또 바뀌어도 영향을 받지 않습니다.

## 집계 컬럼은 그대로입니다

`count` · `sum` · `avg` 는 `BigDecimal` 로 남습니다. Tibero JDBC 가 이들의 precision 을
`0` 으로 보고하는데, 그 경우는 정수로 좁히지 않고 그대로 두기 때문입니다.

```
select avg(v) from T   =>  3.5   (BigDecimal)   ← 소수 정밀도 유지
```

정수로 좁혔다면 `3.5` 가 `3` 으로 깎였을 것입니다.
